Главная нескладность, на мой взгляд, не столько в значениях, сколько в самом ключе: source_type: view внутренне противоречиво — view это как раз то, что источником не является. Назвать вид «типом источника» —
  значит спорить с собственной терминологией дока. Плюс origin и view — не сбалансированная пара (естественный антоним к view — source/base, а к origin — derived).

  Отсюда два направления: либо сменить ключ на нейтральный, либо вообще уйти от «типа» к флагу.

  Варианты
  
  A. Нейтральный ключ + DB-пара source / view
  kind: view      # по умолчанию kind: source
  kind (или role) — пустой контейнер, не навязывает смысл. Пара source/view — прямая аналогия с БД (CREATE VIEW ... FROM <source>), знакома любому. Минус: source всё ещё немного перегружено (у вас уже есть
  source как ссылка на источник в атрибутах вида — будет тёзка).

  B. Пара «авторитетность ↔ производность»: origin / derived
  kind: derived   # по умолчанию kind: origin
  Сохраняет привычный origin, но даёт ему честный антоним. derived точнее, чем view: оно описывает суть (вычислено из чего-то), а не форму подачи. Сбалансированная пара прилагательных-по-смыслу. Мой фаворит,
  если хотите оставить расширяемый перечень.
  
  C. Одиночный флаг (origin — это просто «не view»)
  view: true      # отсутствие атрибута = origin
  Раз origin — значение по умолчанию и его всё равно никогда не пишут, «тип» вырождается в булев маркер. Самый честный и короткий вариант: помечаем только виды, origin не объявляем вовсе. Минус — не
  расширяется, если завтра появится третий тип источника (материализованный вид, кэш и т.п.).
  
  D. presentation / projection (если хочется точности термина)
  data_kind: projection
  projection — формально самое точное слово для вида (проекция данных), но это жаргон; читателю-нетехнарю менее очевидно, чем view.
  
  Сводно

  ┌─────────┬───────────┬─────────────────────┬─────────────────────────────────────────────────┐
  │ Вариант │   Ключ    │      Значения       │                  Когда выбрать                  │
  ├─────────┼───────────┼─────────────────────┼─────────────────────────────────────────────────┤
  │ A       │ kind      │ source / view       │ хотите узнаваемую DB-аналогию                   │
  ├─────────┼───────────┼─────────────────────┼─────────────────────────────────────────────────┤
  │ B       │ kind      │ origin / derived    │ хотите расширяемость и точную пару — рекомендую │
  ├─────────┼───────────┼─────────────────────┼─────────────────────────────────────────────────┤
  │ C       │ —         │ view: true          │ цените минимализм, третий тип маловероятен      │
  ├─────────┼───────────┼─────────────────────┼─────────────────────────────────────────────────┤
  │ D       │ data_kind │ source / projection │ важна терминологическая строгость               │
  └─────────┴───────────┴─────────────────────┴─────────────────────────────────────────────────┘

  Я бы остановился на B (kind: origin | derived) как на расширяемом и семантически чистом, либо на C (view: true), если расширяемость не нужна — он же убирает из спеки целый абзац про «origin по умолчанию
  указывать не обязательно».

  Скажете, какой нравится (или гибрид) — обновлю views.ru.md под него, код не трогая.
